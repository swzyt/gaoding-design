# 浏览器发布流程优化（2026-11-08）

本次修改源码和仓库内运行副本；没有操作生产浏览器、生成素材或修改发布作品。以下是实现范围与验证依据，不是线上速度测试。

## 已实现

1. **新稿的制作完成条件提前检查。** 新 native brief 明确冻结 separation_contract，把用户要求独立的对象映射到不同 layer ID，角色和透明要求随 recipe、spec 与 portable recipe 保存。校验缺对象、同层复用、有效透明、背景约定范围、来源与最终 PNG 内容哈希。每个非背景对象必须单独出现在隐藏审查计划中。同一素材可以用于两个分别可编辑的杯子层。新纯文字/形状稿显式声明空对象契约；旧冻结任务没有契约时标记 legacy-unverified，不伪称验收合格。
2. **稳定浏览器步骤分成两次连续执行。** 新 agent 登记路线在登记和来源证据准备完成后，prepare → bind → audit 共用一次 ego-browser nodejs；实际 04-final 视觉门审查通过后，form → submit → declare → verify 再共用一次。固定序列、同一 Page、串行调用已有函数，不跨越视觉门审查。正常新流程这七步由七次进程调用变为两次；这只证明少五次启动，不代表网页操作或整体耗时下降相同比例。
3. **恢复不会依靠计时日志伪造成功。** 老任务已存在独立阶段记录则沿原单步检查点恢复。批次失败留下失败状态，重跑复用底层恢复保护。publication.json 已明确记录 published:true 且阶段/标题/话题/描述一致时，只跳过重新打开表单，submit 使用既有无点击分支，继续版权声明和核验；submission-started 不确定仍拒绝重发。
4. **浏览器步骤可计时。** browser-sequence.jsonl 记录 step_start、step_success、step_failure、尝试 ID、时间及单调时钟毫秒耗时，不写完整错误文本或敏感 URL。timing-report.json 的 browser_steps 汇总成功、失败、重跑与未结束步骤；未结束时长保持未知。这些时间属于既有 machine spans，不能和总墙钟再次相加。
5. **兼容旧稿。** 没有新契约的历史 spec 保留原有图层字段和图片 box 格式，防止交付重建改变已经审查的 spec 哈希。单阶段 browser CLI 保留。运行副本包含新增模块，不依赖工作区外的新模型或 GD CLI。

## 仍然必须由实际观察完成

结构检查不能判断茶壶是不是茶壶，也不能证明背景没有烘焙残影。不能把冻结对象清单、透明像素或程序成功当作视觉认可。原有逐对象隐藏、恢复、重开、字体、版权以及实际 Agent 审查仍保留。本次未实施凭旧字体回执直接跳过当前编辑器核验，也未用缓存代替版权状态读取。

## 验证

完整 `bash scripts/check.sh` 包含 Python 单元测试、Node 测试、分层故障注入/恢复测试、版权检查和 runtime 构建。新增测试覆盖：缺对象、同层冒充两个物件、透明不合格、内容哈希改变、合法双杯复用、旧任务兼容、同 Page 串行批次、失败即停止、未知提交不重发、提交成功后的版权失败恢复、gate 时效、进程调用次数及计时日志残缺处理。

测试使用本地 fixture/mock，没有登录站点，没有提交真实作品，也没有支付或生成任务。真实发布耗时尚未重测，6–12分钟仅是之前提出的工程目标，不是本次测得的结果。

下一次经授权的实际制作/发布应从新流程执行，按日志比较导入适配、隐藏验收、投稿、版权核验与交付耗时；保留墙钟总时长，区分门审查等待和机器执行，不将无法观测的间隙擅自归类为推理、网络或调试。
